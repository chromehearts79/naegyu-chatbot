# 내규챗봇 브라우저 운영 설계

- 작성일: 2026-11-05
- 상태: 검토자 확인 완료, 사용자 승인 대기
- 범위: 인계 과제 중 2번. 담당자가 브라우저만으로 매주 확인부터 새 판 받기까지 하게 만든다.
- 대체: `docs/superpowers/specs/2026-11-04-windows-move-design.md`(윈도우 설치 방식, 쓰지 않음)
- 앞선 설계: `docs/superpowers/specs/2026-11-04-alio-watch-design.md`(판정 규칙과 원문 비교는 그대로 쓴다)

## 1. 왜 만드나

내규챗봇 유지보수를 담당자에게 넘기려 한다. 담당자는 개발자가 아니다. 지금은 프로그램과 문답 세트가 맥 한 대에 있고, 원본은 만든 사람의 iCloud에 있다.

사용자가 "결과물이 웹페이지인지 프로그램인지부터 정하자"고 했고, 비교 뒤 **브라우저 방식**을 골랐다. 담당자 PC에 아무것도 설치하지 않으니 설치, 회사 보안 프로그램, 월요일에 꺼진 PC, PC 고장 문제가 대부분 사라진다.

## 2. 결과물의 모습

| 층 | 누가 씀 | 형태 |
|---|---|---|
| 챗봇 | 직원 | 웹페이지 한 파일(이미 있음) |
| 관리 도구 | 담당자 | GitHub 화면, 메일, Claude 웹(`claude.ai/code`) |
| 변환·비교·검사·빌드 | 사람이 직접 만지지 않음 | 저장소의 프로그램. GitHub Actions와 Claude 클라우드 세션에서 돎 |

담당자가 하는 일:

| 순서 | 어디서 | 누가 | 무슨 일 |
|---|---|---|---|
| 1. 매주 확인 | GitHub Actions | 자동(월요일 아침) | ALIO 확인, 개정이 잡히면 파일을 `대기/` 에 넣고 원문 비교 |
| 2. 알림 | 메일 → GitHub 이슈 | 자동 | 내규별 알림 글. 바뀐 조문·문답·계산기 수 |
| 3. 고치기 | Claude 웹 | 담당자 + AI | "내규 개정 반영"이라고 말함. AI가 문답을 고치고 검사하고 쉬운 말로 정리 |
| 4. 승인 | GitHub 화면 | 담당자 | 정리를 읽고 합치기 버튼 |
| 5. 새 판 | GitHub Actions | 자동 | 시험, 새 판 파일과 검수표를 내려받는 곳(Release)에 올림 |
| 6. 배포 | 외부망 PC | 담당자 | 받아서 망연계로 폐쇄망에 올림 |

## 3. 목표와 하지 않을 일

**목표**
- 담당자는 브라우저만 있으면 된다.
- 개정 하나가 알림부터 새 판 파일까지 이어진다.
- 매주 확인이 사람 PC와 상관없이 돌고, 멈추면 알 수 있다.
- 사본이 GitHub에 있어 누가 맡아도 이어 갈 수 있다.
- 담당자의 Claude가 이 프로젝트의 주의점을 저장소에서 읽는다.

**하지 않을 일**
- 윈도우 설치 프로그램과 윈도우 대응.
- Vercel 인터넷망 배포와 망연계 자동화(3번 과제), 보완 요청 받기(4번 과제).
- AI를 골라 쓰는 기능(다음 과제). 이번에는 재확인의 문제·답을 파일로 주고받게 해서 나중에 끼울 자리만 둔다.
- 문답 세트 내용이나 검색 동작 변경.

**이렇게 되면 돌아가도 실패다**
- 개정이 없는데 옮긴 것만으로 문답이 "재검수 전"으로 잡힌다.
- 확인이 실패하거나 멈췄는데 담당자가 모른다.
- 담당자가 명령을 쳐야만 넘어가는 단계가 있다.
- 시험에 실패한 판이 내려받는 곳에 올라간다.
- `[개정근거]` 시행문처럼 직원 정보가 든 파일이 GitHub에 올라간다.

## 6. 어떻게 만드나

### 6.1 kordoc 판 고정(가장 먼저)

- 값은 `4.24.1`. `package.json` 과 잠금 파일로 kordoc, jsdom, cfb 판을 고정한다. 파이썬은 `requirements.txt` 로 고정한다.
- `update_rules.py`, `convert.sh`, `alio_compare.py` 가 모두 저장소에 설치된 판을 쓴다. 설치돼 있지 않으면 고정 판을 `npx` 로 받는다.
- 판을 올리는 절차를 `CLAUDE.md` 에 적는다. 전체를 다시 변환해 바뀐 단위를 보고 지문을 다시 찍는 일이라 임의로 하지 않는다.
- 고정 뒤 복무세칙 직전 판 시험 수치(ALIO 설계 5장)를 다시 재고, 달라지면 그 설계의 숫자를 고친다. 직전 판은 ALIO 복무세칙 ZIP에 있다.

### 6.2 저장소

- 공개 저장소 `chromehearts79/naegyu-chatbot`. 담당자가 정해지면 쓰기 권한으로 초대하거나 넘긴다. 저장소, 이슈, 커밋 기록은 누구나 볼 수 있다.
- **원본을 저장소 `원본/` 으로 옮긴다.** 대상은 정확히 72개(내규 71개 한글 파일과 위임전결 별표 엑셀). `[` 로 시작하는 2개와 하위 폴더는 옮기지 않는다. `NAEGYU_SRC` 가 없으면 이 폴더를 쓴다. iCloud 폴더는 지우지 않고 보관본으로 둔다.
- `[` 로 시작하는 파일은 `.gitignore` 로 막는다.
- 줄바꿈 변환으로 지문이 바뀌지 않게 `.gitattributes` 에 `* -text` 를 둔다.
- `data/`, `dist/`, `node_modules/`, `.venv/` 는 저장소 밖이다. 준비 스크립트가 만든다.
- **보호 규칙은 걸지 않는다.** 저장소 쓰기 권한이 있는 담당자가 합치기 버튼을 누른다. 승인자는 한 명이면 된다. 그래서 PR 시험에 실패해도 합칠 수는 있고, 시험 실패 판이 나가지 않게 막는 것은 `release.yml` 의 재시험이다(6.8).
- **봇 커밋:** Actions는 기본 `GITHUB_TOKEN` 으로 main에 직접 커밋한다(`대기/`, `alio_seen.json`). 이 커밋은 다른 워크플로를 시작시키지 않으므로, 한 워크플로 안에서 필요한 일을 다 끝내게 짠다. 별도 토큰을 쓰지 않는다.
- **실행 경계:** 저장소 만들기와 올리기는 사용자 허락(아래 2번) 뒤 작업자가 `gh` 로 한다. 연습 한 바퀴의 Claude 클라우드 단계도 작업자가 클라우드 세션으로 돌린다.

**올리기 전 절차**
1. `scripts/check_upload.py`: 올릴 파일에서 메일·전화번호·주민번호 꼴과 API 키 꼴을 찾고, 원본의 파일 정보를 목록으로 낸다. 전화번호는 알려진 2건만 통과시킨다. 다른 것이 나오면 멈춘다.
2. 사용자에게 저장소 이름, 공개 여부, 파일 목록, 점검 결과를 보여 주고 허락받는다. 건너뛰지 않는다. 공개이므로 이때 함께 정한다.
   - **커밋 작성자 메일:** 원격이 없는 지금은 기록을 고칠 수 있으니 GitHub noreply 주소로 바꾸는 것을 권한다. 한 번 공개되면 되돌리기 어렵다.
   - **내부 자료:** `reports/rule_fix_candidates.md`(내규 오류 후보), `reports/review/`, `reports/review_decisions.json`, `reports/council/`, `reports/governance/`. 올릴지 뺄지 사용자가 정한다. 빼는 경우 운영에 꼭 필요한 파일(`review_decisions.json`)은 대안을 정한다.
3. 올린 뒤 GitHub 파일 목록에 `[개정근거]`, `contacts` 가 없는지 확인한다.

### 6.3 준비 스크립트

`scripts/setup_project.py`. Actions와 Claude 클라우드 세션이 함께 쓴다.

- 잠금 파일대로 패키지 설치, 원본 72개 변환, `build_db`, `data/snapshot_texts.json` 만들기.
- **바뀐 단위 0개, 다시 확인 문답 0장을 확인한다.** 다르면 실패하고 내용을 보여 준다. 지문을 저절로 다시 찍지 않는다.
- 다시 돌려도 안전하다. 이미 된 단계는 건너뛴다.
- 형태소 분석기처럼 큰 패키지는 그 단계에서만 설치한다(선택 인자).
- Claude 클라우드 세션이 시작될 때 자동으로 돌게 저장소 설정(`.claude/settings.json` 의 시작 훅)에 넣는다. 안 되면 스킬 첫 단계에서 돌린다.

### 6.4 매주 확인(`.github/workflows/watch.yml`)

매주 월요일 아침(한국 시간 9시 전후). 손으로도 돌릴 수 있다. 판정은 ALIO 설계 6.1~6.4를 그대로 쓴다(`watch_alio.judge`, `alio_compare.compare_rule`). 새로 만드는 것은 결과를 내는 쪽이다(`scripts/watch_ci.py`).

- **기준값:** 저장소의 `knowledge/alio_seen.json` 과 `원본/` 에서 그때 만든 목록(`build_release`). 배포판 주소를 읽지 않는다. '배포 대기'는 이 흐름에 나오지 않는다.
- **활동 기록:** 공개 저장소는 저장소 활동이 60일 없으면 예약 실행이 저절로 꺼진다. 매주 실행이 `reports/alio_watch/last_run.json` 을 main에 커밋해 활동을 남긴다. 그래도 멈추면 심장 박동 메일로 안다.
- **파일:** 개정 의심 내규의 현행 묶음을 `대기/<내규명>_<파일 날짜>/` 에 넣고 main에 올린다. 챗봇에는 영향이 없다. 커밋 메시지는 CI를 다시 돌리지 않게 표시한다.
- **내규별 이슈 하나:** 판정, 목록 날짜, 게시일, 경과일, 바뀐 조문, 개정 전·후 글자(길면 자름), 다시 확인 문답 수와 목록, 계산기, `대기/` 위치, 다음에 할 일(Claude 웹 링크와 할 말). ALIO 글자는 마크다운이 깨지지 않게 정리한다.
- **같은 내규는 이슈를 새로 만들지 않고 고친다.** 해소되면 저절로 닫는다.
- **미해소 알림:** 판정이 그대로면 매주 댓글을 달아 메일이 가게 한다. 경과 14일이 지나면 "정 담당 확인, 부재면 게시판에 미반영 공지"를 적는다.
- **매주 확인 기록(심장 박동):** 고정한 이슈 하나에 매주 댓글을 단다("이번 주 변동 없음" 또는 개정 의심 목록). 메일이 오지 않는 주는 멈춘 것이다. 안내서에 적는다.
- **확인 실패:** 접속 실패, 응답 이상, 첨부 해석 실패, 준비 스크립트 실패는 "확인 실패" 이슈를 만들거나 고치고 작업을 실패로 끝낸다. "변동 없음"으로 끝나지 않는다. 다음 주에 성공하면 닫는다.
- **담당자 지정:** 저장소 변수 `NAEGYU_ASSIGNEES` 에 GitHub 아이디를 적으면 이슈에 지정해 메일이 가게 한다. 정·부 담당을 함께 적을 수 있다.
- **재시도:** 실패하면 한 번 더 돌린다. 예약 실행이 늦게 시작할 수 있음을 안내서에 적는다.

### 6.5 확인함

재게시처럼 새 판으로 끝나지 않는 알림(ALIO 설계 6.4.1)을 끝내는 길이다.

- 담당자가 이슈에 **`확인함: 사유`** 라고 댓글을 달면 Actions가 `alio_confirm.apply_confirm` 으로 기록하고 이슈를 닫는다. AI가 필요 없다.
- 저장소 쓰기 권한이 있는 사람의 댓글에만 반응한다. 사유가 비면 다시 적어 달라고 답한다.
- 판 번호는 올리지 않는다.

### 6.6 개정 반영(Claude 웹)

스킬을 `.claude/skills/naegyu-update/SKILL.md` 로 옮기고 클라우드에 맞게 고친다. `skills/` 복사본은 없애고, 이 맥의 `~/.claude/skills/naegyu-update` 는 작업 끝에 지우고 알린다.

1. **받기:** `대기/` 와 열린 이슈를 보고 무엇을 반영할지 말한다. 파일을 `원본/` 의 올바른 이름으로 옮기고 `대기/` 에서 지운다. 내규관리부서에서 받은 파일을 담당자가 `대기/` 에 올린 경우도 같다. 다만 ALIO 에 아직 올라오지 않은 내규는 정보보안담당관이 답하기 전에는 이 방법으로 올리지 않고, ALIO 에 올라오기를 기다려 자동 알림을 받는다(저장소가 공개라서다. 올린 뒤에는 `upload_guard.yml` 이 올리면 안 되는 이름의 파일이 있는지 보고 걸리면 `공개 점검 실패` 이슈로 알린다). 새 내규면 분류 코드를 묻는다.
2. **변환·비교:** `update_rules.py convert`. 결과를 쉬운 말로 알린다.
3. **문답 고치기:** 지금 규칙(`knowledge/AUTHORING.md`) 그대로. 검사와 AI 재확인(6.7)까지.
4. **새 판 준비:** `update_rules.py finish`. 판 번호를 올리고 시험을 돌린다.
5. **올리기:** `claude/…` 갈래에 커밋하고 Pull Request를 연다. 본문에 무엇이 바뀌었나(카드마다 한 줄, 계산기, 담당부서 확인 필요 사항)와 "합치기 버튼을 누르면 새 판이 만들어집니다"를 쉬운 말로 적는다. 관련 이슈를 링크한다. Claude가 합치지 않는다.

- `finish` 끝의 ALIO 기록 갱신은 클라우드에서 실패하므로 경고만 내고 지나간다. 실제 갱신은 합친 뒤 Actions가 한다(6.8). 이 때문에 담당자가 놀라지 않게 메시지를 고친다.
- 대화 중 버튼이 없는 환경이므로 다음 할 말을 글로 알려 준다.

**사용 한도:** 고친 카드는 갈래에 자주 커밋한다. 한도에 걸리면 시간이 지난 뒤 "개정 반영 이어서"로 계속한다. 이어서 할 때는 열린 갈래를 찾아 고친 카드를 다시 고치지 않는다. 하위 작업은 새 내규 대량 작성과 재확인 때만 쓴다.

### 6.7 AI 재확인

- `blind_check.py` 에서 로컬 모델 호출을 없애고 나눈다.
  - **문제 만들기:** 고른 문답마다 질문, 인용 조문 원문, 항목 이름을 파일로 쓴다. 답은 넣지 않는다.
  - **채점:** 답 파일을 읽어 지금 규칙(`compare`)으로 판정하고 `reports/blind_check.*` 를 쓴다.
- 답은 스킬이 Claude 하위 작업(기본 Sonnet)에 맡긴다. 문제 파일만 읽고 답 파일만 쓰게 지시한다. 지시문에 의존하는 한계를 안내서에 적는다.
- 클라우드 세션에서 하위 작업이 되는지는 아직 시험하지 않았다. 만들 때 먼저 확인한다. 안 되면 담당자가 **새 Claude 웹 세션**을 열어 재확인만 돌리는 방식으로 바꾼다(문제 파일만 주면 된다). 그때도 비교 규칙은 같다.
- 대상은 고치거나 새로 만든 문답만. 끝난 만큼 파일에 쌓아 이어 갈 수 있게 한다.
- 답 파일에 답한 AI 이름을 적는다. 다음 과제에서 API나 로컬 모델이 같은 파일을 채운다.
- '판정 필요'는 지금처럼 원문과 대조해 고치거나 `reports/review_decisions.json` 에 남긴다. 비교 규칙은 바꾸지 않는다. 만들 때 문답 20장(분야를 고르게 섞어 고정 시드로 무작위 선택)으로 시험해 '판정 필요' 비율을 지금 결과(저장소의 `reports/blind_check.json`)와 비교해 사용자에게 보고한다.

### 6.8 시험과 새 판(`.github/workflows/`)

**Pull Request 때(`check.yml`):** 준비 스크립트 뒤 `check_knowledge.py`, `test_watch_alio.py`, `test_forms.py`, `test_engine.js`, 화면 만들기, `ui_test.js` 를 돌린다. 결과가 PR 화면에 보인다. 실패하면 PR에 쉬운 말로 댓글을 달아 "합치지 말고 Claude 웹에 이 글을 보여 주세요"라고 알린다.

**main에 합쳐졌을 때(`release.yml`):**
- 같은 시험을 돌리고 **통과할 때만** 진행한다.
- `alio_release.py refresh` 로 ALIO 기록을 올려 커밋한다. 관련 이슈가 다음 판정에서 닫히도록, 이 자리에서 바로 판정을 한 번 돌린다.
- 화면 파일을 만들어 GitHub Release에 올린다. 태그는 판 번호. 받는 파일의 실제 이름은 영문 `naegyu-chatbot-vN.html` 이고 화면에는 한글 이름표 `내규챗봇_제N판.html` 이 붙는다(GitHub이 한글 파일 이름을 `_.0.html` 처럼 깨뜨려 올리기 때문). 함께: `artifact.html`, GPTs 묶음, 소관부서 검수표, 바뀐 내용 요약.
- **판 번호 비교:** `knowledge/site.json` 의 `release.no` 를 기존 Release 태그(`v<번호>`)와 비교한다. 태그가 없으면 만들고, 있으면 만들지 않는다. 그래서 다시 돌려도 안전하고, 문서·코드만 고친 경우 올라가지 않는다.
- **PR 시험의 판 번호 검사(`check.yml`):** `원본/` 이나 `knowledge/` 의 문답이 바뀌었는데 판 번호가 최신 태그보다 크지 않으면 실패한다. `finish` 를 빠뜨렸거나 다른 PR이 먼저 합쳐진 경우다. "Claude 웹에 이 글을 보여 주세요"로 안내한다.
- 실패하면 이슈로 알린다.

**동시 실행:** 저장소에 커밋하는 작업들은 겹치지 않게 묶는다.

**Actions 비용:** 공개 저장소의 일반 실행기는 무료로 안내돼 있다. 패키지는 캐시하고 필요한 때만 돈다. 유료 전환은 하지 않는다. 실제 소요를 재서 보고한다.

**공개 저장소 보호:** 다른 사람의 포크 PR에는 비밀값과 쓰기 권한을 주지 않는다(`pull_request` 만 쓰고 `pull_request_target` 은 쓰지 않는다). `release.yml`·`watch.yml` 은 포크에서 돌지 않게 한다. 확인함 댓글은 쓰기 권한이 있는 사람만 반응한다(6.5). 이슈 글에 담당자 이름 등을 적지 않고 GitHub 아이디만 쓴다.
