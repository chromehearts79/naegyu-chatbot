# 내규챗봇 ALIO 확인 루틴 설계

- 작성일: 2026-11-04
- 상태: 검토자 확인 완료, 사용자 승인 대기
- 범위: 인계 후 운영 흐름 중 **① ALIO 확인 ~ ③ 원문 비교**를 자동으로 돌리는 루틴

## 1. 왜 만드나

내규챗봇 유지보수를 관리 담당자에게 넘기려 한다. 내규가 바뀌면 문답 세트도 바뀌어야 하는데, 지금은 만든 사람이 알아서 챙겨야만 개정을 알 수 있다. 석 달(2026년 7~9월)에 16건이 개정될 만큼 잦아서, 사람이 ALIO를 들여다보는 방식으로는 오래가지 못한다.

그래서 매주 자동으로 ALIO를 확인하고, 개정이 잡히면 **"바뀐 조문 몇 개, 고쳐야 할 문답 몇 개, 다시 볼 계산기 몇 종"** 까지 담당자 PC에 미리 알려 주는 루틴을 만든다. 담당자는 이 결과를 보고 개정 반영을 시작한다.

## 2. 전체 흐름에서 이 문서의 자리

| 단계 | 누가 | 무엇을 | 이 문서 |
|---|---|---|---|
| ① ALIO 확인 | 자동(매주) | 배포판과 비교해 개정 의심을 찾음 | **범위 안** |
| ② 원본 받기 | 자동 + 담당자 | 최근 일자 파일을 대기 폴더에 받고, 담당자가 확인 | **받기까지 범위 안** |
| ③ 원문 비교 | 자동 | 바뀐 조문과 고칠 문답을 골라냄 | **범위 안** |
| ④ 문답 세트 고치기 | AI + 담당자 | 문답 고치기·새로 만들기, 계산기 맞추기 | 범위 밖(윈도우 이전 과제) |
| ⑤ 시험·승인 | 자동 + 담당자 | 화면 점검, 검색 시험, 승인 | 범위 밖(윈도우 이전 과제) |
| ⑥ 배포 | 담당자 | 인터넷망(Vercel)과 폐쇄망(망연계)에 같은 파일 | 범위 밖(두 망 배포 과제). 단, 지문 목록을 함께 만드는 일은 범위 안(6.2) |
| ⑦ 검수 | 소관부서 | 바뀐 문답만 확인 | 범위 밖 |

## 3. 목표와 하지 않을 일

**목표**
- 담당자가 ALIO를 직접 보지 않아도 개정을 놓치지 않는다.
- 개정이 잡히면 일의 크기(조문·문답·계산기 수)를 시작 전에 안다.
- PC를 며칠 못 켜도 개정이 빠지지 않고, 늦어질 뿐이다.
- AI 없이 돈다.

**하지 않을 일**
- 챗봇을 자동으로 고치거나 배포하지 않는다. 사람이 개정 반영을 시작한다.
- 내규 원본 폴더와 저장소를 건드리지 않는다. 받은 파일은 대기 폴더에만 둔다.
- 메일·메신저로 보내지 않는다. 결과는 담당자 본인 PC에서 본다.
- 폐쇄망 배포 여부는 확인하지 않는다. 폐쇄망에는 인터넷이 없다.

**이렇게 되면 잘 돌아가도 실패다**
- 헛알림이 잦아서 담당자가 알림을 무시하게 된다.
- 확인에 실패했는데 "변동 없음"으로 보인다.
- 옛 판 파일을 현행본으로 읽는다.

- 목록: `POST https://www.alio.go.kr/item/itemReportListSusi.json`. 본문에 `apbaId: "C0352"`, `apbaType: "A2004"`, `reportFormRootNo: "21110"`, `search_word: ""`, `search_flag: "title"`, `pageNo`. 응답 `data.result`, `data.page`.

- 일부 요청은 User-Agent·Referer가 없으면 거부될 수 있어 함께 보낸다.
- 목록 칸: `stDate`(이 문서에서 '목록 날짜'), `idate`(이 문서에서 '게시일'. 실제 뜻은 ALIO 최종 수정일이라 수정하면 뒤로 밀린다).

**파일 구조**
- 첨부 합계 216개. 46건은 첨부가 여러 개다.

**최근 일자 규칙 시험 결과**

**날짜와 게시 시점**

## 6. 동작

### 6.1 한 번 돌 때의 순서

1. 이번 주에 돌 차례인지 확인한다(6.7).
2. 배포판 지문 목록을 읽는다(6.2).
3. ALIO 목록과 **내규 전체의 첨부 목록**을 받는다(파일은 아직 받지 않는다). 이상하면 멈추고 '확인 실패'로 끝낸다(6.8).
4. 게시일, 목록 날짜, 첨부의 최신 파일(`fileNo`) 중 **하나라도 배포판 기록과 다른 내규만** 고른다. 나머지는 파일을 받지 않는다.
5. 고른 내규의 파일을 받아 현행 묶음을 고른다(6.3).
6. 판정한다(6.4).
7. '개정 의심'은 대기 폴더에 저장하고, 정 담당 PC에서는 원문 비교를 돌린다(6.5).
8. 결과 화면을 만들고 알린다(6.6).

### 6.2 배포판 지문 목록(`release.json`)

공유 폴더가 없으므로, 정·부 담당 PC는 **배포된 판**을 공통 기준으로 삼는다.

`dist/release.json` 을 챗봇 파일과 함께 만들고 함께 배포한다. 내규마다 다음을 담는다.
- 이름, 분류 코드, ALIO `idx`
- 그 판을 만들 때 기록한 ALIO 값: 게시일(`alio_mod`), 목록 날짜(`alio_st_date`), 최신 첨부 번호(`alio_file_no`), 파일 이름 날짜(`alio_file_date`)
- 원본 파일 지문: 한글 파일은 `knowledge/source_files.json` 과 같은 방식(SHA-1 앞 16자리), 엑셀은 칸 값으로 만든 지문
- 판 번호, 만든 날짜, 형식 번호

ALIO 값은 저장소의 `knowledge/alio_seen.json` 에 두고 `release.json` 을 만들 때 옮겨 담는다.

**처음 기록(1회):** 지금의 ALIO 목록과 첨부 목록을 기준으로 `knowledge/alio_seen.json` 을 만든다. 이때 5장의 수치(현행본 날짜 규칙 통과, 새로 올라온 게 없음, 지문이 다른 23건, 같은 달 첨부가 둘이라 지문을 비교하지 못하는 오래된 내규 2건은 알려진 예외)와 맞는지 확인하고, 다르면 멈춘다.

**새 판을 만들 때:** `update_rules.py finish` 에서 ALIO 값을 다시 받는다. 값이 달라진 내규는 현행 묶음의 지문이 새 원본과 같을 때만 기록을 올린다. 같지 않으면 옛 기록을 그대로 두고, finish 출력에 "이 내규는 ALIO 파일과 달라 다음 확인 때 다시 잡힘"을 알린다. 인터넷이 안 되면 경고만 내고 옛 기록을 둔다.

**담당자 확인함:** 6.4.1의 경우에 쓴다. 정 담당 PC에서 명령을 칠 필요 없이 실행하는 작은 프로그램이다. 미해소 내규를 고르고 사유를 적으면, 지금 ALIO 값을 `knowledge/alio_seen.json` 에 사유·날짜와 함께 기록하고 `dist/release.json` 만 다시 만든다. 판 번호는 올리지 않는다. 기준값이 저장소와 배포판에 있으므로 PC별 기준값이 생기지 않는다.

이 방식의 효과:
- PC별 기준값이 없어서 며칠, 몇 주를 건너뛰어도 빠지는 개정이 없다.
- 담당자가 새 판을 올리면 부 담당 PC의 알림도 다음 확인 때 사라진다.

**읽는 곳:** 설정의 `release_url`(HTTPS)이 먼저다. 읽지 못하면 설정의 `release_path`(정 담당은 저장소 `dist/release.json`)를 쓰고, 결과에 "배포판을 읽지 못해 이 PC의 마지막 빌드와 비교함"을 표시한다. 둘 다 없으면 '확인 실패'다. 호스팅이 Vercel이 아니어도 URL만 바꾸면 된다.

### 6.3 현행 묶음 고르기(가장 최근 일자 기준)

1. 첨부, ZIP, ZIP 안의 ZIP(2단계까지)을 모두 열어 후보를 모은다.
2. **파일 이름에서만** 날짜를 읽는다. 폴더 이름은 보지 않는다.
3. 가장 최근 날짜의 파일을 현행으로 고른다.
4. 날짜가 같은 파일은 한 묶음으로 함께 읽는다(위임전결 한글 파일 + 별표 엑셀).
5. 다음을 확인한다. 하나라도 어긋나면 추측하지 않고 '담당자 확인'으로 넘긴다.
   - 날짜를 읽지 못한 파일이 후보에 있다.
   - 최신 날짜에 같은 종류(한글 문서)가 둘 이상이다. 예전 이력의 `_1`, `_2` 표기가 최신 판에 나타나는 경우다.
   - 고른 날짜가 목록 날짜와 다르다. 이름에 일이 있으면 일까지, 월까지만 있으면 월까지 비교한다.

### 6.4 판정

| 판정 | 조건 | 담당자에게 |
|---|---|---|
| 변동 없음 | ALIO 값 셋이 모두 배포판 기록과 같음 | 알리지 않음 |
| 이미 반영 | 현행 묶음의 지문이 배포판과 같음 | 건수만 표시 |
| 글자 변화 없음 | 지문은 다르지만 변환한 **전체 글자**(별지 포함)가 같음. 정 담당 PC에서만 판정 | 건수만 표시, 재게시로 안내 |
| **배포 대기** | 지문이 배포판과 다르지만 저장소 `dist/release.json` 과 같음. 정 담당 PC에서만 판정 | 알림 + "새 판을 올리면 끝남" |
| **조문 밖 변화** | 조문·별표·부칙은 같은데 전체 글자가 다름(별지 등) | 알림 + 달라진 글자 |
| **개정 의심** | 지문이 다르고 위 어디에도 해당하지 않음 | 알림 + 비교 결과 |
| **담당자 확인** | 6.3 확인 불통과 | 알림 + 까닭 |
| **새 내규** | 배포판에 없는 내규 | 알림 + 조문 수 |
| **목록에서 사라짐** | 배포판에 있는데 ALIO 목록에 없음 | 알림. 폐지로 단정하지 않음 |
| **확인 실패** | 6.8 | 알림 + 까닭, 마지막 성공일 |

- 내규 대응은 `idx` 로 하고, 없으면 이름에서 공백·가운뎃점을 지우고 맞춘다. 이 방식으로 71건 모두 대응된다.
- 파일 이름 날짜가 `alio_file_date` 와 같으면 '개정 의심'에 "날짜가 그대로라 재게시일 수 있음"을 덧붙인다.
- 내부와 현행본의 형식이 다르면 "형식이 달라 차이가 과장될 수 있음"을 덧붙인다.
- 판정이 바뀌지 않는 동안 매주 다시 알린다.

#### 6.4.1 알림이 끝나는 길

기본은 **ALIO 파일을 원본으로 반영하고 새 판을 배포**하는 것이다. 지문이 같아지므로 기록이 저절로 올라간다. 그 길로 끝나지 않는 경우는 담당자가 '확인함'으로 끝낸다.

| 경우 | 끝내는 법 |
|---|---|
| 개정 의심, 조문 밖 변화(반영할 내용 있음) | ALIO 파일을 원본으로 넣고 개정 반영 → 새 판 배포 |
| 배포 대기 | 새 판 배포 |
| 글자 변화 없음(재게시) | 다음 새 판을 만들 때 기록을 함께 올린다. 이 경우만 finish가 지문 대신 전체 글자로 판단한다 |
| 조문 밖 변화(반영할 내용 없음), 내부 파일로 반영해 지문이 다름 | 확인함 + 사유 |
| 담당자 확인 | 파일을 보고 반영하거나, 확인함 + 사유 |
| 새 내규를 넣지 않기로 함, 목록에서 사라졌지만 유효함 | 확인함 + 사유 |

확인함을 남긴 값과 ALIO 값이 다시 달라지면 처음부터 다시 판정한다.

### 6.5 미리 원문 비교(정 담당 PC만)

- 저장소의 조문 분리(`scripts/build_db.py`)와 개정 비교(`scripts/check_changes.py`)를 **그대로** 쓴다. 로직을 새로 쓰지 않는다.
- 다만 이 비교는 조문·항·별표·부칙만 본다. 별지는 `build_db.py` 가 제목만 남기므로 본문 변화를 못 잡는다. 그래서 변환본 전체 글자 비교를 **따로 더한다**. 새 판을 만든 뒤 배포 전이면 비교 기준이 이미 새 판이므로, 지문으로 '배포 대기'를 먼저 가른 뒤 비교한다.
- 저장소는 건드리지 않는다. 임시 사본에서 돌리고 지운다(이 방식으로 시험함). 또는 그만큼 안전한 다른 방식이면 된다.
- 변환은 kordoc을 쓰고 버전을 고정한다(현재 4.24.42).
- 결과는 **그 내규 것만** 걸러 보여 준다: 바뀐 조문·별표·부칙, 개정 전·후 글자, 다시 확인 문답 수와 목록, 참고 문답 수, 계산기 이름, 새 조문 수.
- 비교가 실패해도 '개정 의심'은 그대로 알리고, 실패 사유를 함께 적는다.
- 부 담당 PC는 "정 담당 PC에서 비교"로 표시한다.

### 6.6 결과와 알림

**폴더**(`문서\내규챗봇 ALIO 확인\`)
- `이번 주 결과.html`: 쉬운 말로 된 한 장. 맨 위에 "마지막 확인: ○일 전", 이어서 판정별 표(내규명, 목록 날짜, 게시일, ALIO 게시 후 경과일, 판정, 비교 결과, 받은 파일 위치, 원본 폴더에 넣을 때 쓸 파일 이름).
- `기록\YYYY-MM-DD.html`: 매주 결과 보관.
- `기록.csv`: 내규별로 처음 잡힌 날, 해소된 날.
- `대기\<내규명>_<파일 날짜>\`: 받은 현행 묶음.

**알림**
- 표 6.4에서 굵게 쓴 판정이 있으면 윈도우 알림을 띄우고 결과 화면을 연다.
- 없으면 "이번 주 변동 없음" 알림만 띄운다.
- 알림은 설치 없이 되는 윈도우 기본 기능으로 띄운다. 알림이 실패해도 결과 화면은 연다.
- 14일이 지났는데 해소되지 않은 내규는 빨간색으로 표시하고 "정 담당 확인, 부재면 게시판에 미반영 공지"를 안내한다. 경과일은 게시일과 이 PC에서 처음 잡은 날 중 이른 날부터 센다(게시일은 수정하면 밀리기 때문).

### 6.7 언제 도나(PC가 꺼져 있을 때)

- 윈도우 작업 스케줄러에 **매주 월요일 9시**와 **로그인할 때** 두 가지로 등록한다. 사용자가 로그인해 있을 때만 돌린다(알림과 화면을 띄워야 하므로).
- 프로그램 스스로 판단한다: "가장 최근 월요일 9시 이후 성공 기록이 있으면" 조용히 끝난다. 실패했으면 성공 기록을 남기지 않아서 다음 로그인 때 다시 돈다.
- 실패 시 1시간 간격으로 3번 다시 시도한다.
- 동시에 두 번 돌지 않게 잠금을 둔다.
- 등록은 설치 프로그램으로 한 번에 끝난다. `schtasks /create /xml` 처럼 PowerShell 실행 정책에 막히지 않는 방법을 쓴다.

### 6.8 확인 실패로 보는 경우

"변동 없음"으로 끝나면 안 되는 경우다.
- 접속 실패, 시간 초과, 응답이 JSON이 아님, `data.result`·`data.page` 없음
- 받은 건수가 `totalCount` 보다 적음
- 받은 목록이 배포판 내규 수의 절반 미만
- 배포판 지문 목록을 읽지 못함
- 첨부 목록을 해석하지 못함(사이트 개편 의심)

## 7. 윈도우에서 주의할 점

- **인코딩:** 저장소 스크립트는 인코딩을 지정하지 않고 파일을 읽는다. 한국어 윈도우 기본값(cp949)에서는 깨지므로 `python -X utf8` 로 돌린다. 예약 작업 명령에도 넣는다.
- **파이썬:** 3.11 이상(`zipfile` 의 `metadata_encoding` 필요).
- **npx:** 윈도우에서는 `npx.cmd` 로 부른다.
- **파일 이름:** 맥에서 옮겨 온 이름은 한글 자모가 분리돼 있을 수 있다(NFD). 비교 전에 NFC로 맞춘다.
- **경로:** 맥 전용 경로에 의존하지 않고 설정 파일로 받는다.
- **외부망 환경:** 프록시·방화벽·인증서는 실제 PC에서만 확인할 수 있다.

## 8. 보안

- 이 루틴은 AI를 쓰지 않고, ALIO와 `release_url` 외에는 접속하지 않으며, 아무것도 밖으로 보내지 않는다.
- 받은 파일은 믿지 않는 자료로 다룬다.
  - ZIP의 경로를 그대로 쓰지 않는다(폴더 밖으로 나가는 이름 차단).
  - 크기·개수 상한을 둔다.
  - hwp·hwpx·xlsx·zip 외에는 읽지 않는다. 안에 든 프로그램은 실행하지 않는다.
- `release.json` 은 인터넷에 공개되므로 공개 내규의 이름·날짜·지문만 담는다.
- ALIO 요청에 개인 메일 등 개인정보를 넣지 않는다.

## 13. 이 문서 밖에 남은 일

- **윈도우 이전 과제:** 저장소를 담당자 PC로 옮기기(현재 원격 저장소 없음, `data/`·`dist/` 는 저장소에 없음), 전체 개정 반영 절차의 윈도우 대응, 맥 전용 로컬 검증 AI(qwen3.5:35b) 대체.
  - **실제 운영은 이 과제가 끝난 뒤 시작한다**(사용자 결정). 그전에는 맥에서 손으로 돌려 시험만 하고, 맥 자동 실행은 만들지 않는다. 그동안 개정은 지금처럼 직접 챙긴다.
  - 처음 기록은 프로그램을 만들 때 한 번 한다. 그 뒤 맥에서 새 판을 만들면 `finish` 가 기록을 올린다. 그 사이 ALIO에 올라왔지만 반영하지 않은 개정은 운영 첫 주에 잡힌다.
  - 담당자 PC 인수 시험(9장)은 이 과제 뒤에 한다.
- **두 망 배포 과제:** Vercel 올리기, 망연계 절차. `release.json` 을 실제 주소에 올리는 일은 이 과제에서 한다. 그 전에는 정 담당 PC가 `release_path` 로 돈다. 부 담당 PC는 주소가 생긴 뒤에 설치한다.
- **인터넷망 보완 요청 받기 과제**
- **기관 확인:** 정보보안지침 제38조(민간 클라우드 조건) 확인. 결과에 따라 호스팅이 바뀌어도 이 루틴은 `release_url` 만 바꾸면 된다.
- **내규관리부서 확인:** 지문이 다른 24건 중 실제 문구가 다른 곳은 어느 쪽이 맞는지 확인
